## 1. Инженерный вывод

Предложенная последовательность **«снимок данных → запрос ресурсов → кэширование → однократная сборка → проверка геометрии → показ → адресные обновления / контролируемая перестройка» в целом адекватна**. Она устраняет опасное смешение поступления графических ресурсов и структурного `render()`. Но буквальные требования «ожидать абсолютно все иконки всего инвентаря» и «собрать весь DOM вне документа и сразу показать» **нельзя без изменений перенести на архитектуру оригинала**:

1. У клиента уже есть отдельные кэши графики, асинхронная доставка классических спрайтов и ленивая загрузка Morrowind-моделей. Нужен **координатор поверх существующих поставщиков**, а не второй независимый декодер и хранилище сырых файлов.
2. Классическая иконка может отсутствовать по данным/ошибке, а уведомление об этой неудаче не всегда отправляется. Ожидание только `onReady` способно навсегда скрыть окно. У каждого запрошенного ресурса должен быть **конечный исход: готов / отсутствует / ошибка**, при котором допустима штатная буквенная заглушка.
3. `virtualRows` при количестве строк **меньше 120** строит их все; начиная с 120 первоначально строит 48, затем реальный видимый диапазон. Запрашивать всю графику тысяч предметов до открытия окна нельзя: подготавливать следует **то, что требуется для первого представления**, остальные элементы прогреваются по мере прокрутки или необязательно заранее.
4. `virtualRows.sync()` требует подключённого к документу контейнера с измеримой геометрией. Финальная подготовка включает **скрытый подключённый staging-host, измерение и только потом раскрытие**, а не измерение полностью отсоединённого фрагмента.
5. Перестройка **всего окна** должна быть исключением. Смена категории телеги по оригинальному контракту — **переотбор и refill существующего `.remotelist`**, а готовность картинки — **замена содержимого конкретной плитки**.

**Целевая гарантия:** ни незавершённая иконка, ни поступивший поздний ответ старой категории, ни смена категории не могут реентрантно разрушить графический хост, вызвать каскад полных `render()` или показать частично подготовленный интерфейс. Это необходимая архитектурная защита, **не доказательство первопричины** остановки видимого GDI-кадра.

## 2. Что установлено в коде и наблюдениях

- [`fpArm.js:4148–4175`](https://github.com/Lattymoy/daggerfall-js-source/blob/a3eb160/src/combat/fpArm.js#L4148-L4175) и [`fpArm.js:7103+`](https://github.com/Lattymoy/daggerfall-js-source/blob/a3eb160/src/combat/fpArm.js#L7103) — первый запрос модельной иконки может запустить асинхронный `preloadIcon`; завершение уведомляет общих подписчиков `fpArm`, иногда синхронно, даже если разрешённой модели нет. После загрузки `itemIcon` может выполнить **синхронное** `renderGroundMesh`: «сырые байты пришли» ещё не означает «картинка уже готова».

Следовательно, только callback не даёт надёжного признака «все ресурсы завершены».
- [`enhancedInventory.js:4781+`](https://github.com/Lattymoy/daggerfall-js-source/blob/a3eb160/src/ui/enhanced/enhancedInventory.js#L4781) — общий `fpArm.subscribe` исторически запускал полный `render` при уведомлении о фигуре **и** об иконке; [`refreshFigure`](https://github.com/Lattymoy/daggerfall-js-source/blob/a3eb160/src/ui/enhanced/enhancedInventory.js#L837) отдельно способен запустить render после async-композиции персонажа.

### 2.2. Мод и игровой факт

- В исходном баге журнала F-31–F-44 доказана синхронная вложенность `render()` и размножение `.pack-shell`. Предыдущее лечение ввело защиту от реентрантности и владение host/session.
- По ранее документированной трассе `dfo-mod-inventory-trace(3)(1).ndjson` (сводка в предшествующей редакции плана) в 1.29.13 часть смен категории отсоединяла прежние `select.storecat` и `.remotelist` при одном `.pack-shell`. В интервале около 17 секунд GDI-снимок Windows оставался неизменным, хотя Electron heartbeat/логика работали. **Это наблюдение, не доказанный GPU-root-cause.**
- Пользовательский воспроизводитель: телега с 20–40 предметами; сменить броню → оружие **до завершения загрузки иконок**; видимый кадр застывает, Escape даёт слышимый возврат управления, DevTools не появляется визуально. Условие считается обязательным acceptance case.
- В 1.29.14 текущий `src/mod/inventory-transform.cjs` уже отслеживает live tiles и при неизменной `fpArm.status()`-сигнатуре старается обновить их адресно. **Это эвристика**, так как исходный `fpArm.subscribe` не передаёт тип события. Новый конвейер должен проверить и, при необходимости, заменить её строгим контрактом, а не наслаивать рядом ещё один render-trigger.
- **Граница доказательств:** здесь проведён статический анализ читаемого upstream `a3eb160` и текущего GitHub-кода мода. Предоставленная прежде трасса использована по уже зафиксированным в репозитории итогам; повторного анализа её сырых строк и Windows-runtime в этой редакции нет. Конкретный установленный `DFO-Online-game.pack` проверить отдельно перед реализацией.

## 3. Целевой контракт конвейера

### 3.1. Подготовка модели — без DOM

На открытие/смену фильтра создаётся **снимок намерения**: owner, sessionId, revision, remote kind, идентичности предметов, текущие категории/поиск/редкость/материал, выбранный предмет, режим rows/grid, скролл, layout/DPR, generation ресурсов. Сначала выполняется штатный опрос предметной модели и фильтрация; не изменять инвентарь ради визуализации и не доверять устаревшим ссылкам после переноса предметов. Снимок — **не глубокая копия игровых предметов**, а согласованный набор идентичностей и версий; перед публикацией проверить, что актуальное состояние не изменилось.

Источником предметов и законности действий остаётся оригинальная игровая модель. Изображение не должно влиять на возможность переместить, взять, экипировать предмет или завершить закрытие.

### 3.2. Подготовка ресурсов — без полного render

По снимку вычислить ресурсы **первоначально нужного изображения**: видимые ряды актуальной категории, бумажная фигура/её штатный fallback, выделенная карточка, необходимые статические элементы. Для 20–40 видимых записей обычный `virtualRows` создаёт все строки; для крупных списков — только исходный диапазон/overscan с последующей догрузкой при прокрутке. Фоновый прогрев остального набора возможен, **но не входит в барьер открытия**.

Использовать штатные `requestIcon/requestFittedPicture`, `fpArm.itemIcon/preloadIcon`, `ITEM_ICON_CACHE` и кэши текстур/моделей. Создать **тонкий адаптер статусов**, который отличает:
- `ready` — рисунок реально доступен в нужном размере/варианте;
- `pending` — загрузка либо подготовка модели/текстуры продолжается;
- `absent` — у предмета нет применимого изображения;
- `failed` — запрос завершился ошибкой; разрешён штатный fallback;
- `cancelled` — результат принадлежит утратившему силу owner/revision.

`absent` и `failed` считаются **завершёнными**, а не поводом вечно ждать или повторять запрос. Дедупликация одновременных запросов по устойчивому ключу: generation + вид источника + record/model + материал/окраска + box/scale/DPR. Ключ иконки **не равен** только индексу предмета. Кэшировать подготовленные изображения и уже существующие нативные результаты **в рамках игровой сессии и действующего поколения ресурсов**, без повторной декодировки на каждый фильтр; не дублировать тяжёлые бинарные payload в собственном Map. При настоящей смене source generation, масштаба, DPI или контекста графики инвалидировать только зависящие записи. На выходе из игры нативные кэши завершают свой жизненный цикл.

**Важно:** текущие API не дают единого `Promise.all(images)` с достоверным terminal-status: для classic `missed()` нет wake, у model `null` неоднозначен. **Сначала требуется минимальный диагностируемый ресурсный контракт**, а не цикл опроса `itemIcon()`, не бесконечная очередь микрозадач, не произвольный timeout/лимит «40 иконок». Синхронную генерацию модельных иконок нужно отделить от графического mount и измерять отдельно; если она дорогостоящая, допустить уступку event loop между естественными стадиями подготовки, без синхронного ожидания в UI thread.

### 3.3. Одна сборка, скрытое измерение, атомарная публикация

Для **новой структурной ревизии** (новое окно/существенно изменённая модель):
1. До начала DOM-работ убедиться, что текущие запросы первого экрана имеют конечные результаты. Допустимы реальные картинки и штатные fallback; необязательные иконки будущих строк не блокируют.
2. Выполнить **одну** сборку DOM по неизменному снимку, без публикации частичного окна и без возможности вложенного `render()`. Любой notice во время построения записать как данные для следующей ревизии либо адресного обновления — **не запускать вторую сборку поверх первой**.
3. Присоединить новый хост в **визуально скрытом, но измеримом** состоянии (не `display:none`); после этого выполнить `virtualRows.sync`, геометрию `dfo_pack`, восстановление прокрутки и проверку ошибок. Не утверждать, что чисто detached DOM способен вычислить корректные размеры.
4. Проверить owner/session/revision и item-snapshot. Если запрос устарел, **не раскрывать** его, освободить все принадлежащие ему обработчики/virtualRows/ожидатели и начать актуальную ревизию; не уничтожать более новый host.
5. В одной контролируемой фазе **вывести из владения и полностью демонтировать прежнюю оболочку**, установить новый единственный активный shell и раскрыть готовое окно. Ввод разрешить только после установки обработчиков, измерения, публикации и завершения commit. Событие закрытия/Escape должно оставаться доступным в любом состоянии.
6. Если подготовка/сборка падает, снять блокировку в `finally`, не оставлять полумонтированные окна/вторые подписки. Сохранить прежний исправный UI, если он ещё принадлежит этой сессии, либо штатно закрыть неудавшийся новый UI с ошибкой; не оставлять невидимую вечную блокировку.

**Точность термина «один раз»:** один структурный build/commit на **принятую ревизию**, а не «одно построение на всю игровую сессию». Настоящие изменения модели и действий игрока по-прежнему имеют право создать следующую ревизию. Загрузка пикселей уже показанной плитки сама по себе **не является** новой структурной ревизией.

### 3.4. Фильтрация и поздние иконки

Фильтр категории — **операция над списком**, не новая `.pack-shell`:

1. Захватить нужный `storecat/storesearch/storerarity/storemat` и новую ревизию фильтра; подготовить отобранные item IDs и начальный набор графики, пока старый **стабильный** экран остаётся целым. На время операции локально запретить конфликтующие повторные item-действия/клики фильтра, но **не** заблокировать игру, Escape или DevTools; последнюю запрошенную категорию сохранить (last-write-wins).
2. В защищённой, нерекурсивной операции выполнить **один** `fillRemoteList(list,true)`/аналог над тем же list, корректно `dispose` старый virtualRows и создать новый; сохранить свойства фильтров, фокус, selection и скролл по их штатным правилам. Не допускать переплетения с полным `render`.
3. Когда модельная/классическая иконка поздно стала готова, проверить owner + session + generation данных + filterRevision + конкретный item/key + подключённость holder. Подменять **только графическое содержимое существующей плитки**, сохраняя `.itemrow`, handlers, drag/drop, wear bar, rare/quickslot chips. Для offscreen items достаточно наполнить native cache; их строки родятся при прокрутке.
4. Ни `fpArm icon-ready`, ни `landingTiles` callback не разрешено трансформировать в полный `render()` из-за отсутствия картинки. Настоящее изменение фигуры/экипировки и `refreshFigure` обрабатывать **отдельным типом события**, с правом адресной перерисовки figure либо одного нового структурного commit, если изменились данные.
5. Завершение операции и снятие локальной блокировки — в `finally`, включая исключение и отмену; stale callbacks не могут мутировать DOM следующей категории.

При этом *первый* показ новой категории можно задержать до завершения её обязательных ресурсов, но нельзя искусственно заморозить кадр всей игры: видимая предыдущая версия интерфейса остаётся целой либо показывается штатный неинтерактивный локальный loading-state, не частично собранный список. Не использовать busy-spin, синхронные ожидания или безусловные повторные rebuild.

### 3.5. Полная реконструкция и жизненный цикл

Полный rebuild нужен для открытия/закрытия сессии, смены типа окна/существенной структуры, реального изменения набора/свойств предметов, смены режима отображения и изменений, которые нельзя безопасно выразить локальным refill. Его единственный путь: **cancel старой работы → prepare нового снимка/ресурсов → build → attach/measure → dispose старого владельца → commit/reveal**.

Запретить параллельные полные rebuild одного host, синхронную рекурсию, бесконечное dirty/retry и перенос результатов от закрытой сессии A в B, включая повторный mount в тот же host. `unmount` обязан освобождать подписку `fpArm`, виртуализаторы, drag, клавиатуру, resize, иконочные ожидатели, registries и pending promise-continuations по generation. Настоящий выход из инвентаря не должен ждать графику. Не ломать native overlay unregister, pending chest save, dropped items и `onDismiss`.

## 4. Порядок будущей реализации

**Этап 0 — база и привязка к исполняемому клиенту (обязательный gate).** Установить точный установленный Electron build и SHA asset, сверить реальный минифицированный `enhancedInventory`, `fpArm`, `textureCanvas`, `virtualRows` и сигнатуры инъекций. Закрепить воспроизводитель «20–40, броня→оружие до готовности», контроль без тяжёлого DOM monkey-patch, фиксацию фактического Windows-кадра и состояние источников иконок. Зафиксировать, что в текущем коде 1.29.14 уже работает, прежде чем менять его. При несовпадении сигнатуры — **fail closed**, не молчаливый пропуск hook.

**Этап 1 — события и readiness.** В минимальной совместимой точке разделить сообщения `icon settled` (с ключом и исходом) и `figure/model changed`. При невозможности безопасно изменить исходный контракт — написать adapter вокруг проверенных поставщиков ресурсов; не путать `fpArm.status()`-эвристику с доказанным типом. Проверить отдельно model/no-model, classic success/missed, синхронные и async callbacks, смену gen. Тест: каждая попытка получает один terminal-outcome, не создавая full render.

**Этап 2 — ресурсный coordinator и кэш.** Считать инвентарный snapshot; выделить первый экран; подготовить, дедуплицировать и кэшировать графику через существующие native APIs. Доказать, что 20–40 холодных предметов не создают повторные запросы после возврата к категории. Показ с fallback должен состояться и при корректно зафиксированном missing icon. Не включать весь архив предметов в обязательный барьер.

**Этап 3 — state machine render и транзакционный commit.** Ввести состояния `CLOSED → PREPARING → BUILDING → MEASURING → READY`, плюс `CANCELLING/FAILED`, ownership tokens и revision. Обернуть структурные входы `render`/mount, не ломая native item actions; отдельный staging, присоединение для измерений, единственный publish. Все исключения и отмены чистятся. Тест: один host, один `.pack-shell`, без рекурсии и без демонстрации недостроенного UI.

**Этап 4 — filter-refill без структурного render.** Интегрировать `storeFilterBar` и `fillRemoteList` с coordinator. Last-write-wins, отмена устаревшего prefetch, единый refill/virtualRows sync; поздние иконки адресно, никакой замены `select`/`.remotelist` по icon-ready. Настоящие item mutations запускают корректную новую ревизию, а не остаются невидимыми.

**Этап 5 — сохранение регрессий мода.** Оставить геометрию 1.29.5, обе раскладки, размеры двух режимов, девять категорий, панель персонажа, resize/DPR, zoom, hover, scroll/caret, quickslots, drag/drop, sort, junk, transfer, экипировку, paper doll, закрытие, A→B и same-host remount. `dfo_pack.js` менять только при отдельном подтверждённом конфликте измерений.

**Этап 6 — тесты на реальных применённых assets.** Unit/integration: cold 1/20/40/119/120/600+ вещей; async success/error/absent; ранняя смена категории; скролл и поздняя строка; 40 уведомлений без full render; owner A→B; close-before-load; refreshFigure во время refill; DPI/resize; release после ошибки. CI должен подтверждать применение каждого необходимого hook **к тестируемому game pack**, не только валидность Node mocks. Отдельно проверить CPU long tasks и отсутствие незавершённого promise/registry роста, без глобального тяжёлого DOM probe в производительном прогоне.

**Этап 7 — живой Windows Electron acceptance.** Несколько серий точного пользовательского воспроизведения: холодная телега 20–40, броня→оружие до завершения иконок, ещё категории, обратно; rows/grid; затем прогретый кэш, 120+ и большой контейнер; Escape и движение мира, открытие DevTools. Проверить **изменение фактических Windows-пикселей** нужных областей на известные действия, а не один `renderer.heartbeat`, `capturePage`, звук шагов или число DOM-нод. Если GDI-кадр по-прежнему стоит — **релиз заблокирован**, возвращаться к механизму presentation/compositor на проверяемой базе, не объявляя pipeline-функцию GPU-фиксом.

**Рекомендуемый порядок коммитов реализации:** readiness events → resource adapter/cache → coordinator/staging → filter refill + targeted tile updates → lifecycle/cleanup → tests + applied-bundle check. Каждая стадия должна быть проверяема и откатываема независимо.

## 5. Обязательные инварианты и запреты

| Инвариант | Проверка |
| --- | --- |
| Одна активная сессия/owner и один видимый `.pack-shell` | DOM и тест A→B/remount |
| Никаких полных `render()` от одного icon-ready | счётчик причинных вызовов, 1/20/40 уведомлений |
| Смена категории не уничтожает select/remote-list | node identity, connected-state, focus, virtualRows |
| Окно не видно недостроенным, ввод включается после commit | функциональный тест стадии подготовки/публикации |
| Каждый обязательный ресурс заканчивается ready/absent/failed; stale отменяется | fixture classic missed, no-model, async reject |
| `virtualRows` измерен только после attach; offscreen рождается при скролле | 119/120/600+, layout/scroll acceptance |
| Предметные транзакции и выход не зависят от загрузки картинок | transfer/equip/drop/Escape в ходе prefetch |
| Результат не считается исправлением без Windows visual test | фактический кадр и интерактивный UI в Electron |

**Не применять:** таймеры как способ скрывать рекурсию; искусственное ограничение числа предметов; бесконечное ожидание заведомо отсутствующей графики; полную перестройку на `onReady`; отключение GPU/смену драйверов как замену исправления lifecycle; постоянную блокировку всего игрового ввода; переписывание `fpArm` или `virtualRows` целиком без доказанной необходимости. Предварительная подготовка выполняется асинхронно с уступкой event loop, **никакого busy waiting на главном JS-потоке**.

**Решение для текущего запроса:** принять эту архитектуру как технический план, **но не считать её автоматически лучшей, чем минимальный точечный фикс 1.29.14**. Сначала объективно проверить существующий icon-only путь на живом Electron. Если он устраняет визуальную остановку без новых дефектов, внедрять полную staging-машину исключительно ради красоты конвейера не требуется; если нет — строить её по описанным воротам и сохранять точную классификацию событий. Сам код пока не изменён.
